# Глоссарий: расшифровка и значение всех аббревиатур из бэклога

Ниже собрано всё, что новичок может не понять в карточках задач: сначала сокращённые префиксы идентификаторов задач, затем аббревиатуры процесса, затем технологические, затем «почти-аббревиатуры» из терминологии TimSort, и в конце — жаргонизмами, которые не являются сокращениями, но требуют перевода. Имена классов и методов Java (`CustomArrayList`, `CompletableFuture`, `Files.lines` и т.п.) — это идентификаторы кода, а не аббревиатуры, и они не расшифровываются.


## 1. Роли и Scrum-процесс

| Аббревиатура | Расшифровка | Что значит |
|---|---|---|
| TDD | Test-Driven Development — разработка через тестирование | Базовая дисциплина проекта: сначала пишется падающий тест, затем минимальный код до его прохождения, затем рефакторинг. В наших правилах тест обязан «увидеть красный» до появления реализации |
| PO | Product Owner — владелец продукта | Отвечает на вопрос «что и зачем делаем»: ведёт бэклог, расставляет приоритеты, формулирует критерии приёмки, принимает истории. В команде совмещён с ролью SM и принадлежит участнику A |
| SM | Scrum Master | Хранитель процесса: фасилитирует церемонии, следит за времябоксами, устраняет препятствия. Scrum Master не начальник, а сервисная роль для команды |
| DoR | Definition of Ready — определение готовности (к работе) | Чек-лист, при выполнении которого задачу можно брать в спринт: декомпозирована до ≤1,5 чел-дня, есть критерии приёмки, ясны владелец и зависимости |
| DoD | Definition of Done — определение готовности (работы) | Чек-лист завершённости: тесты написаны первыми и видели красный, зелёный CI, рефакторинг выполнен, Javadoc на публичных методах, PR одобрен и смержен |
| CI | Continuous Integration — непрерывная интеграция | Автоматический запуск сборки и всех тестов при каждом Pull Request; в проекте это GitHub Actions, выполняющий `mvn test`. Правило «мерж только при зелёном CI» — механизм, который физически не даёт нарушить TDD-дисциплину |
| PR | Pull Request — запрос на слияние | Форма попадания кода из ветки разработчика в `main`: коллега ревьюит изменения, CI их проверяет, и только после одобрения происходит слияние. В GitLab то же самое называется MR (Merge Request) |
| WIP | Work In Progress — работа в процессе | WIP-лимит — правило «не более одной задачи в работе у человека одновременно», защищает от распыления |
| Mob | mob programming — «программирование толпой» | Формат работы, когда вся команда сидит за одним экраном и пишет код вместе; наша mob-сессия по TimSort нужна, чтобы алгоритм понимали все трое, а не один человек |
| AAA | Arrange–Act–Assert — «расставь–выполни–проверь» | Каноническая структура теста из трёх блоков: подготовка данных, выполнение тестируемого действия, проверка результата. Требование конвенции TEST-1 |
| Scrum | не аббревиатура | «Схватка» — термин из регби, давший имя фреймворку; частая ошибка — пытаться расшифровать его как акроним |

## 2. Инженерные принципы, технологии и инструменты

| Аббревиатура | Расшифровка | Что значит |
|---|---|---|
| API | Application Programming Interface — программный интерфейс | Публичный «контракт» класса или библиотеки — методы, которыми пользуется остальной код. «Запрещённые API» в наших задачах — готовые реализации из стандартной библиотеки (`Arrays.sort`, `Collections.frequency` и т.п.), которые нельзя использовать по условию задания |
| SOLID | акроним пяти принципов ООП-дизайна | S = SRP (Single Responsibility, единственная ответственность), O = OCP (Open/Closed), L = LSP (Liskov Substitution, подстановка Барбары Лисков), I = ISP (Interface Segregation, разделение интерфейсов), D = DIP (Dependency Inversion, инверсия зависимостей). Архитектура проекта построена на всех пяти; в карточках напрямую упомянут OCP |
| OCP | Open/Closed Principle — принцип открытости/закрытости | Класс должен быть открыт для расширения, но закрыт для модификации. Пример из INT-1: новая команда меню добавляется регистрацией новой лямбды, а не правкой кода цикла меню |
| DRY | Don't Repeat Yourself — «не повторяйся» | Каждое знание в системе должно существовать ровно в одном месте. Пример из CODEC-1: формат строки файла определён в одном кодеке, который используется и для чтения, и для записи |
| UI | User Interface — пользовательский интерфейс | Всё, что видит пользователь; в нашем случае — текстовое консольное меню |
| UX | User Experience — пользовательский опыт | То, как система ведёт себя с человеком; «UX-политика» в SRC-3 — решения вроде «при неверном вводе переспрашивать, а не падать» |
| UML | Unified Modeling Language — унифицированный язык моделирования | Стандартная графическая нотация для диаграмм классов, последовательностей, состояний; в README они описываются текстом на Mermaid |
| CSV | Comma-Separated Values — значения, разделённые запятыми | Текстовый формат табличных данных «значение;значение;значение». Исторический разделитель — запятая, у нас точка с запятой, но формат по традиции всё равно зовут CSV |
| JDK | Java Development Kit — набор инструментов Java-разработчика | Компилятор, стандартная библиотека и утилиты, в том числе генератор документации Javadoc |
| Javadoc | Java + documentation | Стандартный способ документирования: комментарии особого вида `/** … */` у публичных методов превращаются утилитой JDK в справочную документацию; требование DoD — «публичные API с Javadoc» |
| mvn | команда Maven — системы сборки | Maven управляет сборкой и зависимостями; `mvn test` — прогнать все тесты, `mvn package` — собрать готовое приложение |
| JAR | Java ARchive — Java-архив | Формат файла, в который упаковывается готовое Java-приложение (результат `mvn package`) |
| JUnit | Java + unit (unit — единица, юнит-тест) | Стандартный фреймворк для написания автотестов на Java; «JUnit 5» — актуальная версия. Все `@Test`, `@TempDir` и ассерты в проекте — оттуда |
| JaCoCo | Java Code Coverage — покрытие кода Java | Инструмент, показывающий, какие строки кода выполнялись при прогоне тестов, в процентах; ориентир проекта — ≥85% на пакетах ядра |
| Stream API | потоковый программный интерфейс Java | Декларативная обработка последовательностей данных (`Stream.generate`, `map`, `collect`); заполнение коллекций через стримы — обязательное доп. задание 3 |

## 3. Термины TimSort

Это не сокращения, а устойчивые имена частей алгоритма; новичку они нуждаются в переводе не меньше, чем аббревиатуры.

| Термин | Расшифровка | Что значит |
|---|---|---|
| TimSort | Tim + sort | Гибридная сортировка, названная по имени автора — Тима Питерса, создателя CPython. Это именно тот алгоритм, что стоит за стандартной сортировкой объектов в Java, — поэтому задание требует написать его самостоятельно |
| run | «серия» | Непрерывный уже упорядоченный фрагмент массива; минимальная единица, с которой работает алгоритм |
| minRun / minRunLength | minimum run length — минимальная длина серии | Число в диапазоне 32–64: серии короче достраиваются сортировкой вставками до этой длины |
| MIN_MERGE | минимальный порог слияния | Константа 32: массивы короче TimSort целиком сортирует вставками, не переходя к механике серий и слияний |
| MIN_GALLOP | минимальный порог галопа | Константа 7: если при слиянии одна серия «побеждает» 7 раз подряд, включается режим галопирования |
| mergeLo / mergeHi | merge low / merge high — слияние «нижней» / «верхней» | Две симметричные процедуры слияния соседних серий: mergeLo копирует во временный буфер левую (меньшую) серию, mergeHi — правую |
| gallop, gallopLeft / gallopRight | «галоп» | Оптимизация поиска позиции вставки: сначала позиция ищется прыжками с удвоением шага (1, 2, 4, 8…), затем бинарным поиском внутри найденного диапазона; Left/Right — с какой стороны серии вставляем |
| red / green | красный / зелёный | Словарь TDD из индикатора тест-раннера: «красный» — тест падает (ожидаемо, кода ещё нет), «зелёный» — проходит. «Тест видел красный» — доказательство, что тест действительно проверяет код, а не проходит всегда |

## 5. Жаргон из карточек, не являющийся аббревиатурой

Эти слова постоянно встречаются в описаниях задач, и новичку стоит знать их перевод.

**Коммит** — зафиксированный снимок изменений в Git. **Ревью** (code review) — проверка PR коллегой до слияния. **Аппрув** (approve) — одобрение ревьюером. **Мерж** (merge) — собственно слияние ветки в `main`. **Тег** — именованная метка на коммите; наш тег `v1.0.0` означает версию 1.0.0 (мажорная.минорная.патч-версия) и отмечает точку релиза. **README** — «прочти меня», главный документ в корне репозитория.

**Фейк** (fake) — тестовый двойник: упрощённая, но рабочая подмена реальной зависимости (FakeConsoleIO «играет» консоль). **Шпион** (spy) — двойник, который запоминает, как его вызывали (так проверяется «делегат вызван ровно один раз»). **Стаб** (stub) — заглушка, возвращающая заготовленный ответ (стаб Sorter, пока реальный TimSort не готов). **Оракул** — эталонная реализация, с которой сравнивается результат тестируемого кода; наш оракул — простая сортировка вставками. **Фаззинг** (fuzzing) — массовый прогон тестируемого кода на случайных входах со сравнением с оракулом. **Сид** (seed) — начальное число генератора случайных чисел; фиксированный сид делает «случайный» тест воспроизводимым: при падении он повторится точно так же. **Edge case** — граничный случай: пустой список, один элемент, все элементы равны. **Round-trip** — «туда и обратно»: тест кодирует объект в строку, декодирует обратно и сравнивает с исходным. **Регрессия** — повторное появление уже исправленного бага; регрессионный тест фиксирует исправление навсегда. **Багфикс** (bug fix) — исправление ошибки; по правилам проекта — только через предварительно написанный красный тест.

**Composition root** — «корень композиции»: единственное место в программе (класс Application), где создаются все конкретные реализации и связываются друг с другом. **Optional** — тип-контейнер Java «значение может отсутствовать», используется вместо null и исключений. **@TempDir** — аннотация JUnit 5, создающая временную папку для теста и удаляющая её после (temporary directory). **Времябокс** — встреча с жёстким лимитом времени (стендап — 10 минут, ревью — 30). **Стендап** (или daily) — короткая ежедневная встреча «что сделано / что делаю / что мешает». **Ретро** — ретроспектива, встреча об улучшении процесса. **Демо** — демонстрация работающего продукта в конце спринта. **QA** (Quality Assurance — обеспечение качества) — общепринятое название роли тестировщиков; упоминается потому, что наш префикс QUA намеренно выбран отличным от него, чтобы не создавать ложных ассоциаций.
