# Руководство по управлению ветками и слияниями для новичков

Этот документ — рабочий регламент для команды из трёх человек (A, B, C) на все три спринта. Здесь описано всё, что нужно делать с ветками и слияниями: как правильно начать проект, как работать каждый день, что делать при конфликтах или ошибках в автоматической проверке (CI), и как в последний день выполнить главное требование задания — слить три личные ветки участников в `master`.

Каждый шаг сопровождается командами и коротким объяснением «зачем это нужно», чтобы правила не казались произвольными. Если что-то пошло не так — обращайтесь к разделу 8.

## 0. Общая картина: какие ветки существуют и зачем они нужны

В репозитории всегда есть ветки четырёх видов. У каждой своя роль и свой срок жизни:

| Ветка | Сколько живёт | Кто пишет | Куда сливается | Назначение простыми словами |
|---|---|---|---|---|
| `master` | постоянно | никто напрямую | — (в неё только вливают) | Главная ветка-витрина. Заморожена с первого дня до финальной церемонии. В самом конце в неё по очереди вливают три dev-ветки |
| `a/dev`, `b/dev`, `c/dev` | все 3 спринта | только владелец | в `master` в самом конце | Личная ветка участника, как требуется в задании. Всегда должна быть «зелёной» (проходить проверки). Каждое утро в неё вливают изменения из веток соседей |
| `b/<задача>` (задачные ветки) | несколько дней, пока задача не закрыта | только владелец | в свою же dev-ветку через PR | Временная ветка для одной задачи. Сюда можно коммитить любые промежуточные наработки. Здесь ревьюер смотрит изменения перед тем, как они попадут в dev |
| `merge-rehearsal` | один вечер третьего спринта | A, локально | никуда | Черновик для репетиции финальных слияний. После использования удаляется |

На этих ветках выполняются три главных правила (инварианта):

1. **`master` изменяется только через Pull Request (PR), и только три раза за проект.**  
   Прямая запись (push) в `master` запрещена настройками репозитория. Всё, что попадает в `master`, предварительно проходит автоматическую проверку (CI) и ревью другим участником.

2. **Dev-ветка всегда «зелёная».**  
   В неё попадает только код, который прошёл ревью и автоматические проверки. Все незавершённые наработки живут в задачных ветках. Зелёная dev-ветка — это обещание соседям, что их утреннее слияние не сломает проект.

3. **Чужой код мы только «втягиваем» к себе, свой — только «упаковываем» в PR.**  
   Никто не пушит напрямую в чужие ветки. Никто не коммитит напрямую в свою dev-ветку (кроме слияний с чужими изменениями по утрам).

Интеграция (объединение кода) работает по принципу «втягивания»: каждое утро каждый участник вливает изменения соседей в свою dev-ветку. Только в последний день все dev-ветки вливаются в `master`. Так мы выполняем требование задания («каждый работает всё время в своей ветке, сливаемся в конце»), не теряя при этом ежедневного обмена кодом.

## 1. Первый день: подготовка репозитория

Порядок действий важен, потому что личные ветки должны быть созданы от `master`, который уже содержит необходимую инфраструктуру: файл настройки CI (`.github/workflows/ci.yml`), шаблон PR, файл `pom.xml` с подключённым JaCoCo (инструмент для измерения покрытия кода тестами).

### Шаг 1. Участник A создаёт базовую инфраструктуру

Участник A выполняет начальную настройку:

- Создаёт ветку `master` с первым коммитом.
- Затем создаёт ветку `a/bootstrap`, в которой готовит инфраструктуру (CI, шаблон PR, pom.xml).
- Открывает Pull Request из `a/bootstrap` в `master`.  
  **Важно:** это единственный ранний PR в `master` за весь проект. Он содержит только инфраструктуру, без кода конкретных задач, поэтому не нарушает требование «работать в своей ветке».
- После того как PR принят (влит в `master`), на `master` включается защита ветки. С этого момента `master` замораживается до финального дня.

### Шаг 2. Каждый участник создаёт свою dev-ветку

Теперь каждый участник (включая A) создаёт свою личную dev-ветку от свежего `master`.  
Выполните следующие команды в терминале:

```bash
git fetch origin                  # получить актуальную информацию о ветках с сервера
git checkout master               # переключиться на локальную ветку master
git pull origin master            # подтянуть последние изменения из удалённого master
git checkout -b a/dev             # создать новую ветку a/dev и переключиться на неё
                                   # (для участника B: git checkout -b b/dev, для C: git checkout -b c/dev)
git push -u origin a/dev          # отправить новую ветку на GitHub и запомнить связь
```

После выполнения этих команд ваша dev-ветка появится на GitHub и будет связана с локальной.

### Как проверить, что всё сделано правильно

- На странице репозитория на GitHub во вкладке «Branches» видны четыре ветки: `master`, `a/dev`, `b/dev`, `c/dev`.
- Попытка запушить что-то напрямую в `master` отклоняется (потому что включена защита).
- В вашей dev-ветке существует файл `.github/workflows/ci.yml` (это можно проверить через интерфейс GitHub или командой `ls .github/workflows`).

## 2. Ежедневный ритуал: утренний синк

**Синк** (от английского sync — синхронизация) — это процесс вливания чужих dev-веток в свою собственную. Зачем это нужно? Чтобы три личные ветки (`a/dev`, `b/dev`, `c/dev`) всё время оставались максимально похожими друг на друга. Тогда финальное слияние в последний день пройдёт легко и быстро, а любые проблемы совместной работы кода всплывут уже на следующее утро, а не в последний момент перед сдачей.

Порядок синка называется **«хаб»** (от английского hub — центр, узел): сначала все изменения стекаются к участнику A, а затем от него расходятся к B и C.  

**Почему именно так?** Если один и тот же конфликт (противоречие в коде) возникает у двух людей, его нужно решить **один раз и в одном месте** — у A. Иначе B и C могут решить его по-разному, и тогда ветки снова разойдутся.

### Шаг 1. A вливает к себе ветки B и C

Участник A выполняет команды:

```bash
git checkout a/dev          # переключиться на свою dev-ветку
git fetch origin            # получить свежую информацию о ветках с GitHub
git merge origin/b/dev      # влить изменения из ветки B в свою ветку
git merge origin/c/dev      # влить изменения из ветки C в свою ветку
git push origin a/dev       # отправить обновлённую ветку a/dev на GitHub
```

Что здесь происходит по сути: A берёт последние версии веток B и C и объединяет их со своей. Если при выполнении `merge` возникает конфликт (когда одни и те же строки кода изменены по-разному), нужно разрешить его вручную — инструкции в разделе 5.  

После команды `push` на сервере запускается автоматическая проверка (CI) для объединённого состояния всех трёх веток. Именно в этот момент чаще всего выявляются **конфликты интеграции** — ситуации, когда по отдельности код работает, а вместе ломается.

### Шаг 2. B и C вливают к себе ветку A

Теперь участники B и C по очереди подтягивают к себе обновлённую ветку A (в ней уже содержатся их собственные вчерашние наработки, поэтому этот шаг почти всегда проходит без конфликтов).

Для участника B:

```bash
git checkout b/dev          # переключиться на свою dev-ветку
git fetch origin            # получить свежую информацию
git merge origin/a/dev      # влить изменения из ветки A в свою ветку
git push origin b/dev       # отправить обновлённую ветку b/dev на GitHub
```

Для участника C — аналогично, но с `c/dev` вместо `b/dev`.

### Шаг 3. Обсуждение на стендапе

Первый вопрос на стендапе (короткой встрече команды): **«Зелёные ли синки?»** То есть успешно ли прошли утренние слияния и проверки.

**Красный синк** (когда автоматическая проверка не прошла) — это **блокер всего дня**. Его нужно исправить до начала любой новой работы. Красный синк означает, что код формально объединился, но при совместной работе возникла логическая ошибка — так называемый **семантический конфликт**. Чем дольше откладывать исправление, тем сильнее будут расходиться ветки, и тем сложнее будет потом всё собрать.

### Если A недоступен

Если участник A перегружен или отсутствует, утренний синк может провести любой из B или C, используя те же самые команды. Главное — сохранить принцип «один конфликт решается один раз», а не то, кто именно это делает.

> **Важно:** не отставайте от соседей больше чем на один день. Чем дольше ветки живут отдельно, тем больше накапливается различий и тем серьёзнее будут конфликты при следующем объединении.

## 3. Цикл работы над задачей: от ветки до удаления

Этот цикл вы будете повторять для каждой задачи из бэклога (списка задач). Правило простое: **одна задача = одна отдельная ветка = один Pull Request (PR)**.

**WIP (Work In Progress)** — ограничение на количество одновременно выполняемых задач: у вас в работе не может быть больше одной задачи одновременно.

### Шаг 1. Создать задачную ветку от свежей dev-ветки

«Свежая» dev-ветка — это ваша ветка **после утреннего синка** (раздел 2). Именно это проверяет пятый пункт чеклиста в PR (см. шаг 3). Имя ветки должно быть в формате: `<ваш_логин>/<ID_задачи>`. Например, `b/JFP-2` — ветка участника B для задачи JFP-2.

Команды:

```bash
git checkout b/dev          # переключиться на свою dev-ветку (убедитесь, что она свежая)
git checkout -b b/JFP-2     # создать новую ветку b/JFP-2 и переключиться на неё
```

**Зачем нужна отдельная ветка?**  
- Pull Request (а значит ревью, чеклист, автоматические проверки, кнопка слияния) существует **только между двумя ветками**. Если коммитить напрямую в dev, PR не создать.  
- Это «карантин»: сюда можно пушить любые промежуточные наработки, не боясь сломать общую dev-ветку.  
- На этой ветке можно «заморозить» прерванную работу, просто оставив её как есть.

### Шаг 2. Работать в порядке TDD (красный → зелёный)

TDD (Test-Driven Development — разработка через тестирование) означает: сначала пишете тест, который падает (красный), потом минимальный код, чтобы тест прошёл (зелёный). В вашей ветке вы можете делать любые промежуточные коммиты, но перед отправкой на ревью **порядок коммитов должен быть понятным**: сначала коммит с тестом, затем коммит с реализацией.

Удобно делать два коммита на каждый цикл изменений:

```bash
# 1. Красный: добавили тест, который пока не проходит
git add src/test/...
git commit -m "test(JFP-2): stack run invariants restore"

# 2. Зелёный: написали минимальную реализацию, чтобы тест прошёл
git add src/master/...
git commit -m "feat(JFP-2): implement mergeCollapse invariants"
```

Названия коммитов начинаются с `test:` или `feat:` и содержат ID задачи — так легче потом разбираться в истории.

### Шаг 3. Отправить ветку на GitHub и открыть Pull Request

**Важная особенность нашей настройки CI (Continuous Integration — автоматической проверки кода):**  
Когда вы пушите коммиты в задачную ветку, проверки **не запускаются**. CI включается только когда вы открываете Pull Request. Поэтому до открытия PR можно спокойно пушить промежуточные состояния, не боясь «засорить» историю проверок.

Отправьте ветку на GitHub:

```bash
git push -u origin b/JFP-2    # отправить ветку на GitHub и запомнить связь
```

Затем на странице репозитория на GitHub нажмите кнопку **«Compare & pull request»** (Сравнить и создать запрос на слияние).

**Очень важно указать правильную базу (куда вливать):**  
В поле «base» (базовая ветка) выберите **вашу собственную dev-ветку** (например, `b/dev`), а не `master`.  
То есть PR должен выглядеть как `b/JFP-2 → b/dev`.

Заполните описание PR по шаблону. В шаблоне есть чеклист:

- тесты действительно были «красными» (то есть вы запускали их до реализации и они падали);
- не использованы запрещённые API (например, `Arrays.sort`, `Collections.sort/binarySearch/frequency`, `Stream.sorted`, готовые паттерны);
- публичные методы имеют Javadoc (описание);
- ветка создана от свежей dev;
- проведена самопроверка (например, прогнали тесты локально).

Если работа ещё не завершена, но вы хотите показать коллеге промежуточный результат, откройте **Draft PR** (черновой PR). Это явный сигнал: «не сливать».

### Шаг 4. Ревью и слияние

**Ревьюер** — кто-то из коллег (не автор PR). Назначьте его в интерфейсе GitHub. Если автоматическая проверка (CI) **красная**, кнопка слияния будет заблокирована настройками защиты. В этом случае нужно исправить ошибку в своей ветке (дополнительные коммиты) и запушить изменения. CI перезапустится автоматически после каждого нового пуша. Это нормально, не считайте перезапуск поломкой. После того как ревьюер одобрил изменения и CI зелёный, можно нажимать кнопку **Merge** (Слияние).

**Метод слияния:** разрешён только **«Create a merge commit»** (создать коммит слияния).

**Запрещены** squash (сжатие всех коммитов в один) и rebase (перебазирование) на протяжении всего проекта. Дело в том, что merge-коммит сохраняет в истории видимый след того, что работа велась в отдельной ветке. Это важно и для финальной картины (когда три dev-ветки сольются в master), и для соответствия требованию задания.

После успешного слияния GitHub предложит кнопку **«Delete branch»** (удалить ветку). Нажмите её. Затем удалите ветку и локально:

  ```bash
  git checkout b/dev            # переключиться обратно на dev-ветку
  git branch -d b/JFP-2         # удалить локальную ветку
  ```

Флаг `-d` (маленькая буква) — это защита: git откажется удалять ветку, если она не была слита. Если уверены, что ветка больше не нужна, можно использовать `-D` (большая), но лучше сначала разобраться.

Задачную ветку после слияния удалять безопасно: коммиты из неё уже лежат в dev-ветке.

### Шаг 5. Распространение задачи коллегам

Вашу слитую задачу **не нужно** вручную «проталкивать» в чужие ветки. Это произойдёт автоматически на следующем **утреннем синке** (раздел 2), когда каждый участник втянет к себе изменения из ветки A (которая, в свою очередь, уже содержит ваши изменения).  
Прямое вмешательство в чужие ветки запрещено правилом «чужой код только втягиваем, свой передаём только через PR».

## 4. Вы как ревьюер

Проверка чужого кода (ревью) — такая же часть вашей работы, как написание собственного. Хорошее ревью помогает находить ошибки на ранней стадии и поддерживать качество кода. Вот правильный порядок действий.

**1. Сначала проверьте результат автоматической проверки (CI).** На странице Pull Request вы увидите статус проверки. Если он **красный** (то есть проверка не прошла), значит код сейчас не работает как надо. В этом случае **сразу отправьте PR обратно автору** с комментарием, что нужно починить CI.

**2. Прочитайте описание PR и чеклист.** Автор должен был заполнить, что сделано, и отметить пункты чеклиста (например, что тесты видели красный, нет запрещённых API и т.д.). Обратите внимание, всё ли заполнено и понятно. Если описание пустое или слишком общее — попросите дополнить. Особое внимание обратите на два момента:

- **Порядок коммитов:** в истории коммитов PR тест должен идти раньше реализации. Это видно по названиям коммитов (`test(...)` перед `feat(...)`).
- **Запрещённые API:** поищите в diff использование таких методов, как `Arrays.sort`, `Collections.sort`, `Collections.binarySearch`, `Collections.frequency`, `Stream.sorted`, а также готовые паттерны (например, если задача подразумевает написать свою сортировку). В шаблоне PR перечислены эти запреты.

**3. Прочитайте изменения (diff) как чужой код.** Diff — это список изменённых строк. Читайте его внимательно, как будто вы видите этот код впервые. Старайтесь понять логику. Задавайте себе вопросы: «Понятно ли, что делает этот код?», «Есть ли лишнее или забытое?», «Нет ли ошибок?».

**4. Оставляйте конкретные комментарии.**  
Вместо расплывчатого «переделать» напишите точно, что и почему: например, «здесь ты используешь `Stream.sorted`, а по условию задачи это запрещено — нужно написать свою сортировку». Чем конкретнее замечание, тем быстрее автор его исправит.

**5. Нажмите «Approve» только тогда, когда сами готовы нажать «Merge».**  
Одобрение — это ваша подпись: «я проверил и считаю, что это можно вливать». Если у вас остались сомнения или вы бы не слили этот PR прямо сейчас — не одобряйте, а напишите, что нужно исправить.

**Важно:** никогда не нажимайте кнопку слияния (Merge) для PR, который вы не читали.

## 5. Разрешение конфликтов

Конфликт возникает, когда вы и ваш коллега независимо изменили **одни и те же строки** одного файла. Когда вы пытаетесь слить ветки (например, во время утреннего синка), Git не может сам решить, чью версию оставить, и останавливается с сообщением:

```
CONFLICT (content): Merge conflict in src/...
```

Это нормальная рабочая ситуация. Ниже — пошаговый план, как её разрешить.

### Пошаговый порядок действий

**Шаг 1. Посмотрите, какие файлы конфликтуют.** Выполните команду:

```bash
git status
```

Git покажет список файлов, в которых есть конфликт (обычно они помечены как `both modified`).

**Шаг 2. Откройте каждый конфликтный файл в редакторе.** Внутри файла вы увидите специальные маркеры:

```
<<<<<<< HEAD
... ваш вариант кода ...
=======
... чужой вариант кода ...
>>>>>>> origin/...
```

Всё, что находится между `<<<<<<< HEAD` и `=======` — это **ваша** версия (то, что было в вашей ветке до слияния). Всё, что между `=======` и `>>>>>>> origin/...` — **версия из ветки, которую вы вливаете** (из ветки соседа).

**Шаг 3. Решите, каким должен быть итоговый код.** Удалите маркеры (`<<<<<<<`, `=======`, `>>>>>>>`) и оставьте правильный вариант. Это может быть:

- только ваш код,
- только чужой код,
- **комбинация** (самый частый случай): например, сосед добавил новый метод, а вы добавили новый импорт — в итоговом файле должны остаться и метод, и импорт.

Главное правило: **не теряйте чужую работу**. Внимательно посмотрите, что именно изменил коллега, и сохраните это, если оно не противоречит вашим изменениям.

**Шаг 4. Сохраните файл и сообщите Git, что конфликт разрешён.** После того как вы убрали маркеры и оставили итоговый код, сохраните файл. Затем выполните:

```bash
git add <имя_файла>
```

Повторите это для каждого конфликтного файла.

**Шаг 5. Завершите слияние.** Когда все конфликты разрешены и файлы добавлены, выполните:

```bash
git commit
```

Git сам подставит стандартное сообщение о слиянии (обычно «Merge branch 'origin/...' into ...»). Можно просто сохранить это сообщение.

**Шаг 6. Отправьте результат на GitHub.** Выполните:

```bash
git push
```

Теперь конфликт разрешён, и проверки запустятся заново.

### Важные правила разрешения конфликтов

**1. Конфликт с чужим кодом разрешается вместе с его автором.** Не решайте конфликт молча, выкидывая чужие изменения. Если вы не уверены, что оставить, позовите автора кода (или напишите ему) и разберитесь вместе. Именно поэтому наш утренний синк организован через «хаб» (участник A): конфликт между B и C разбирается **один раз** у A, а затем готовое решение расходится к B и C. Так мы не получаем две разные версии решения одной и той же проблемы.

**2. Конфликт в идее, а не в коде.** Иногда вы с коллегой написали разный код для одного и того же места, и оба подхода имеют право на жизнь (например, два разных алгоритма). В таком случае не решайте спор «кто позже смержил, тот и прав». Вынесите вопрос на стендап (ежедневную встречу) и обсудите. Это поможет выбрать лучшее решение для всей команды.

**3. Горячие файлы требуют особого внимания.** «Горячие» файлы — это файлы, которые часто изменяются всеми участниками, и конфликты в них наиболее вероятны. В нашем проекте это:

- `Application.java` (точка входа, «composition root», где собираются все зависимости);
- карта команд меню (файл, где перечислены все команды);
- `BusComparators.java` (класс с компараторами);
- `pom.xml` (конфигурация сборки).

Правило для горячих файлов:

- **Объявляйте о намерении изменить горячий файл в чате команды ещё *до* того, как сделаете коммит.** Это предупредит коллег и снизит шанс одновременной правки.
- **Правки файла `Application` всегда согласовывайте с участником A.** Так мы избегаем хаоса в главной точке сборки приложения.

## 6. Красный CI: что делать

Красный CI (красная иконка проверки) означает, что автоматическая проверка кода не прошла. Это сигнал, что нужно остановиться и разобраться. Вот типичные ситуации и что делать в каждой.

### Ситуация 1. Красный CI в вашем собственном Pull Request

Если вы открыли PR из задачной ветки в свою dev-ветку, и проверка упала (красный), главный источник информации — **упавший тест**. В этом случае посмотрите лог проверки.

**Что именно делать:**

1. Откройте страницу PR на GitHub, найдите секцию с проверками (обычно внизу, рядом с кнопкой Merge). Нажмите на ссылку с логом упавшей проверки.
2. В логе найдите имя упавшего теста (например, `StackTest.testSomething`) и сообщение об ошибке (какой ассерт не сработал).
3. Воспроизведите проблему локально, запустив только этот тест:

   ```bash
   mvn test -Dtest=ИмяТеста
   ```

   Это быстрее, чем гонять все тесты, и вы сразу увидите ту же ошибку.
4. Исправьте код на своей задачной ветке, сделайте коммит и запушьте. CI перезапустится автоматически.

**Особый случай: CI красный, а локально все тесты зелёные.** Это почти всегда означает, что вы забыли закоммитить какой-то файл, и на сервер уехала неполная версия. Проверьте:

- Выполните `git status` — нет ли незакоммиченных или неотслеживаемых файлов.
- Сравните хеш последнего коммита локально и на GitHub: локально `git log -1` покажет SHA (длинную строку), а на GitHub на странице коммитов или в PR виден SHA последнего коммита. Если они не совпадают, значит, локально есть коммиты, которые не запушены.

Самая частая причина: забыли сделать `git add` для файла с тестом или с реализацией.

### Ситуация 2. Красный CI в dev-ветке после утреннего синка

Если после утреннего слияния чужих веток в вашу dev (или в ветку A, которая потом разошлась) CI стал красным — это **семантический конфликт интеграции**: код по отдельности работает, а вместе ломается. Это **блокер дня**: его нужно чинить до начала любых новых задач, потому что красная dev-ветка — это обещание, которое мы даём друг другу, что синк не сломает проект.

**Что делать:**

- Посмотрите, какие изменения пришли в последнем синке (diff между предыдущим состоянием и текущим). Вероятный виновник — тот, чьи изменения вызвали конфликт логики.
- Свяжитесь с этим участником, разберитесь вместе и исправьте. Обычно проблема в том, что два человека изменили поведение одного и того же компонента несовместимым образом.
- После исправления запушьте исправленную dev-ветку, чтобы CI снова стал зелёным.

### Ситуация 3. Красный CI после хотфикса коллеги на его dev

Если вы заметили, что у коллеги в его dev-ветке CI красный (например, он влил срочное исправление, и оно что-то сломало), **не молчите**. Напишите автору изменения, сообщите о проблеме. Ваш следующий утренний синк всё равно принесёт это изменение к вам, и красный CI может распространиться. Лучше предупредить заранее, чтобы коллега успел починить до того, как вы начнёте синк.

## 7. Мораторий, репетиция и финальное слияние (спринт 3, дни 4–5)

Этот раздел описывает завершающий этап проекта. К этому моменту все основные задачи выполнены, и нужно правильно свести три dev-ветки в `master`, как требует задание.

### Последний обмен и мораторий

**Вечером 4-го дня** участник A в последний раз вливает к себе ветки B и C:

```bash
git checkout a/dev
git fetch origin
git merge origin/b/dev
git merge origin/c/dev
git push origin a/dev
```

После этого объявляется **мораторий**: до конца проекта **никто не вливает чужой код в свою dev-ветку**.

Зачем это нужно? Если продолжать синкаться до самого конца, все три ветки станут практически идентичными. Тогда второй и третий финальные PR в `master` окажутся пустыми — Git скажет «нечего мержить». А по условию задания нам нужно, чтобы **три настоящих, видимых слияния** попали в историю `master`. Поэтому мы фиксируем состояние веток на момент моратория и дальше каждый работает только в своей ветке.

Работа над задачами при этом не останавливается — просто каждый продолжает коммитить в свою dev (через обычные задачную ветку и PR, но база — своя dev), не вливая к себе соседей.

### Репетиция финального слияния

Чтобы финальная церемония не стала импровизацией с сюрпризами в виде конфликтов, днём 4-го дня A выполняет **локальную репетицию**. Он создаёт временную ветку, сливает в неё все три dev-ветки, смотрит, где конфликты, и затем удаляет ветку. Это делается **локально, без пуша** на GitHub.

Команды:

```bash
git checkout -b merge-rehearsal a/dev   # создать временную ветку от a/dev
git merge b/dev                         # попробовать слить b/dev
git merge c/dev                         # попробовать слить c/dev
# ... смотрим, какие конфликты возникли, разбираемся ...
git checkout a/dev                      # вернуться обратно на a/dev
git branch -D merge-rehearsal           # удалить временную ветку ( -D, т.к. она не слита)
```

Если на репетиции обнаружены конфликты, их нужно **разрешить вместе с авторами немедленно** — например, оформить маленькие PR прямо в этот вечер, чтобы к утру 5-го дня конфликтов не осталось.

### Финальное слияние (день 5): три последовательных PR в `master`

В день 5 выполняются три Pull Request'а **по очереди**. Каждый PR — это слияние одной dev-ветки в `master`. Важен порядок и назначение ревьюеров.

**1. Первый PR: `a/dev → master`**  
Это самый большой диф, потому что в `a/dev` к этому моменту накоплены все общие изменения (после последнего синка перед мораторием).  
Ревьюеры: **B и C**.  
Метод слияния: **Create a merge commit** (как и везде).  
Перед мержем убедитесь, что CI зелёный и оба ревьюера одобрили (Approve). Нажмите Merge.

**2. Второй PR: `b/dev → master`**  
Диф будет **маленьким** — это только те коммиты, которые участник B сделал после моратория.  
Ревьюеры: **A и C**.  
Мерж аналогично.

**3. Третий PR: `c/dev → master`**  
Тоже маленький диф — коммиты C после моратория.  
Ревьюеры: **A и B**.

**Почему такой порядок?**  
Мы сливаем сначала ветку, которая содержит больше всего общего кода, а затем ветки с «хвостами» индивидуальной работы. Так каждый PR получается осмысленным, и в истории `master` остаются три явных merge-коммита.

**Условия для кнопки Merge в каждом PR:**  
- Зелёный CI (автоматическая проверка).  
- Хотя бы один аппрув от ревьюера (на практике назначайте обоих — это финальное кросс-ревью, когда каждый смотрит на итоговый код).

### Тег релиза

После того как все три PR слиты в `master`, создайте тег, чтобы зафиксировать версию:

```bash
git checkout master
git pull origin master      # подтянуть последние изменения (включая три merge-коммита)
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0      # отправить тег на GitHub
```

Демонстрация (показ работы) выполняется именно **с тега**, а не с последнего коммита master — так мы точно знаем, какая версия демонстрируется.

В истории `master` после финального слияния остаются три merge-коммита с названиями вида `Merge branch 'a/dev'`, `Merge branch 'b/dev'`, `Merge branch 'c/dev'`. Это и есть **прямое, видимое доказательство** того, что требование задания (слить три ветки участников в `master`) выполнено.

### Если после тега найден баг

Это нормальная и предусмотренная ситуация. Не нужно откатывать тег. Порядок действий:

1. Исправьте баг в **своей dev-ветке** обычным способом: создайте задачную ветку от dev, напишите красный тест, реализуйте фикс, откройте PR в свою dev (как в разделе 3).
2. После того как фикс слит в dev, откройте **PR из вашей dev в `master`** (например, `b/dev → master`). Такой PR — это дополнительное слияние dev-ветки в master, и оно совершенно законно: ветки участников могут сливаться в master не один раз. Требование задания от этого не нарушается, а наоборот, показывает, что вы умеете поддерживать проект после релиза.

При таком PR назначьте ревьюера, дождитесь зелёного CI и аппрува, затем мержите. После этого при желании можно выпустить новый тег (например, `v1.0.1`).

## 8. Типовые проблемы и их решения

Здесь собраны распространённые неприятности и способы их исправить. Если вы столкнулись с чем-то, чего нет в списке, — спросите коллег.

### «Случайно закоммитил прямо в dev, минуя задачную ветку»

Такое бывает: забыли создать отдельную ветку и сделали коммит прямо в `b/dev`. Действия зависят от того, отправили ли вы этот коммит на GitHub (запушили) или он пока только локально.

**Если коммит ещё не запушен (существует только на вашем компьютере):**

1. Создайте новую задачную ветку от текущего состояния dev — в неё попадёт ваш коммит:
   
   ```bash
   git checkout -b b/quick-task
   ```
   Теперь вы на ветке `b/quick-task`, и ваш коммит здесь.

2. Верните dev-ветку к состоянию, которое было до вашего случайного коммита (то есть к последней версии с GitHub):
   ```bash
   git checkout b/dev
   git reset --hard origin/b/dev
   ```
   Флаг `--hard` отбрасывает незапушенный коммит в dev, потому что он уже сохранён в ветке `b/quick-task`.

3. Дальше работайте по обычному циклу: из ветки `b/quick-task` откройте PR в `b/dev`, пройдите ревью и слияние.

**Если коммит уже запушен в `origin/b/dev`:**

Удалить его оттуда без force-push нельзя (force-push в dev запрещён). Поэтому:

- Если изменение **тривиальное** (например, опечатка в комментарии или пробел) — просто сообщите об этом на стендапе. Команда примет к сведению, и ничего страшного не произошло.
- Если изменение **нетривиальное** (реальная логика) — оформите его «задним числом» как нормальную задачу:

  1. Определите коммит, который был до вашего случайного. Можно посмотреть историю: `git log origin/b/dev` и найти предыдущий SHA.
  2. Создайте отдельную ветку от этого предыдущего коммита:
     ```bash
     git checkout -b b/retro-fix <sha_предыдущего_коммита>
     ```
  3. Перенесите ваш случайный коммит в эту ветку:
     ```bash
     git cherry-pick <sha_вашего_случайного_коммита>
     ```
     (SHA можно найти в `git log origin/b/dev` — это последний коммит).
  4. Запушьте ветку и откройте PR из неё в `b/dev` как обычно.
  5. После того как PR одобрен и слит, ваша dev-ветка получит этот код уже через правильный процесс. Временное наличие лишнего коммита в истории dev не критично, главное — что ревью пройдено.

Если что-то не получается — позовите участника A, он поможет.

### «Кнопка Merge не активна (серая)»

Если на странице PR кнопка слияния недоступна, причин обычно две:

1. **Красный CI** — автоматическая проверка не прошла. Посмотрите блок с проверками внизу PR: если есть красный крестик, нужно починить (раздел 6).
2. **Нет одобрения (Approve)** — ревьюер ещё не нажал «Approve» или написал замечания. Дождитесь одобрения и исправьте комментарии.

Также убедитесь, что вы сами не являетесь единственным ревьюером (нужен кто-то другой). Если всё зелёное и есть аппрув, но кнопка всё равно неактивна — возможно, у вас нет прав на слияние; попросите владельца репозитория.

### «Нечаянно удалил задачную ветку или потерял коммиты»

Git хранит все коммиты, на которые когда-либо указывали ветки или HEAD, даже если сама ветка удалена. Восстановить можно через `git reflog` — журнал перемещений HEAD.

Выполните:

```bash
git reflog
```

Вы увидите список записей вида `SHA HEAD@{n}: commit: ...`. Найдите строку, которая соответствует вашему потерянному коммиту (по сообщению или времени). Скопируйте SHA (длинный набор символов). Затем создайте ветку с этого коммита:

```bash
git branch b/восстановленная <sha>
```

Теперь ветка снова существует, и вы можете продолжить работу.

### «Задачная ветка разрослась до тысячи строк»

Это признак того, что задача слишком большая — её не разбили на части. Такое случается, когда пытаются сделать «всё сразу». Правильный путь: остановиться, рассказать о проблеме на стендапе и вместе с командой разбить задачу на две (или больше) подзадачи. Для каждой подзадачи создайте свою ветку и свой PR. Так ревью будет проходить быстрее, а риск ошибок снизится.

### «Хочу переделать историю задачной ветки (rebase или force-push)»

Иногда возникает желание «почистить» историю: переставить коммиты, объединить их или изменить сообщения. Технически на **задачной ветке** (до слияния) это возможно, но для новичка есть простое правило:

> **Никакого force-push нигде и никогда.**

Force-push перезаписывает историю на удалённом сервере, и если кто-то уже скачал вашу ветку, возникнет путаница. Если вам действительно нужно переписать историю (например, вы допустили ошибку в сообщении коммита и хотите исправить), **позовите участника A** — он поможет сделать это безопасно.

## 9. Шпаргалка

Этот раздел — краткий справочник основных команд. Используйте его, когда нужно быстро вспомнить последовательность действий. Подробные объяснения ищите в соответствующих разделах выше.

### Утренний синк для участника A

Участник A первым собирает к себе изменения от B и C, затем отправляет объединённую ветку на GitHub.

```bash
git checkout a/dev && git fetch origin
git merge origin/b/dev && git merge origin/c/dev
git push origin a/dev
```

После этого CI проверит общее состояние. Если возникли конфликты — разрешите их (раздел 5), затем завершите слияние.

### Утренний синк для участников B и C

B и C после A втягивают к себе уже объединённую ветку `a/dev`. Для B:

```bash
git checkout b/dev && git fetch origin
git merge origin/a/dev && git push origin b/dev
```

Для C команды те же, но вместо `b/dev` — `c/dev`.

### Начало новой задачи

Создайте задачную ветку от своей dev-ветки (убедитесь, что она свежая — после утреннего синка) и отправьте её на GitHub.

```bash
git checkout b/dev && git checkout -b b/JFP-2
git push -u origin b/JFP-2
```

Далее работайте в этой ветке, делайте коммиты в порядке TDD, затем откройте Pull Request в `b/dev`.

### Разрешение конфликта

Когда при слиянии возникает конфликт, сначала посмотрите, какие файлы затронуты:

```bash
git status
```

Откройте каждый конфликтный файл, найдите маркеры `<<<<<<<`, `=======`, `>>>>>>>`, удалите их и оставьте правильный итоговый код (при необходимости согласуйте с автором). Затем добавьте файлы и завершите слияние:

```bash
git add <файлы> && git commit && git push
```

Подробности — в разделе 5.

### Закрытие задачи (после Merge на GitHub)

Когда PR слит, удалите ветку на GitHub (кнопка Delete branch) и локально:

```bash
git checkout b/dev && git branch -d b/JFP-2
```

Флаг `-d` защитит от случайного удаления неслитой ветки.

### Локальная проверка перед пушем

Перед отправкой изменений на GitHub полезно прогнать все тесты локально, чтобы не ловить красный CI лишний раз:

```bash
mvn test
```

## 10. Свод правил «всегда / никогда»

В этой таблице собраны главные договорённости команды. Если сомневаетесь, как поступить, — сверьтесь с ней.

| Всегда | Никогда |
|---|---|
| Синк каждое утро; красный синк — блокер дня | Не отставать от соседей больше чем на день |
| Задачная ветка — от свежей dev, PR — в свою же dev | Коммитить прямо в dev (кроме синков) |
| Тест раньше реализации в порядке коммитов | Мержить непрочитанный PR; ставить галочки чеклиста «на потом» |
| Конфликт с чужим кодом разрешается вместе с автором | Разрешать конфликт молча, «выиграв» его |
| Merge-коммит как единственный метод слияния | Squash, rebase-merge, force-push (без A) |
| Удалять задачную ветку после слияния | Держать мёртвые ветки в списке |
| PR в `master` — только три финальных (+возможные хотфиксы) | PR из задачной ветки в `master`; прямой push в `master` |
| Объявлять правки горячих файлов в чате до коммита | Молча менять `Application`, карту команд, `pom.xml` |

Поясню каждую строку подробнее.

**Синк каждое утро** — это обязательный ритуал (раздел 2). Если синк «красный», то есть CI упал после слияния, это блокер: сначала чиним, потом работаем. **Никогда не отставайте от соседей больше чем на день** — иначе конфликты будут накапливаться.

**Задачная ветка всегда создаётся от свежей dev** (после утреннего синка), а PR открывается из задачной ветки **в свою же dev**. **Не коммитьте напрямую в dev** — только через PR из задачной ветки. Исключение: утренние синки, когда в dev попадают чужие изменения.

**В истории коммитов тест должен идти раньше реализации** (TDD). **Не мержите PR, который не читали**, и не отмечайте пункты чеклиста «на потом» — только после реальной проверки.

**Любой конфликт с чужим кодом решайте вместе с автором этого кода.** Не выкидывайте чужую работу молча и не «побеждайте» просто потому, что вы мержите позже. Если конфликт не в коде, а в идее — обсуждайте на стендапе.

**Для слияния веток используйте только «Create a merge commit».** Запрещены squash (сжатие коммитов), rebase-merge и force-push. Force-push в dev-ветку запрещён безусловно. Если очень нужно переписать историю задачной ветки — обратитесь к A.

**После успешного слияния задачную ветку удаляйте** (и на GitHub, и локально). Не оставляйте мёртвые ветки, чтобы не путаться.

**PR в `master` открываются только три раза в финале** (по одному на каждую dev-ветку) и, при необходимости, после релиза для хотфиксов. **Из задачной ветки PR в `master` не открываем**, и прямой push в `master` запрещён настройками.

**Правки горячих файлов** (`Application`, карта команд меню, `BusComparators`, `pom.xml`) **объявляйте в чате заранее**, до коммита. Изменения `Application` согласовывайте с участником A. Не меняйте эти файлы молча — это снизит количество конфликтов.
