# Руководство по управлению ветками и слияниями для новичков

Это рабочий регламент команды из трёх человек (A, B, C) на все три спринта. Здесь собрано всё, что нужно делать с ветками и слияниями: как начать, как работать каждый день, что делать при конфликтах и красном CI, и как в последний день корректно выполнить требование задания — слить три ветки участников в `master`. Каждый шаг сопровождается командами и коротким объяснением «зачем», чтобы правила не выглядели произвольными. Если что-то пошло не так — идите в раздел «Типовые проблемы».

## 0. Картина целиком: какие ветки существуют и почему

В репозитории всегда есть ветки четырёх видов, и у каждой — своя роль и свой срок жизни:

| Ветка | Сколько живёт | Кто пишет | Куда сливается | Смысл |
|---|---|---|---|---|
| `master` | вечно | никто напрямую | — (в неё сливают) | Витрина. Заморожена с первого дня до финальной церемонии; в конце в неё трижды вливают dev-ветки |
| `a/dev`, `b/dev`, `c/dev` | все 3 спринта | только владелец | в `master` в самом конце | «Ветка участника» из задания. Интеграционная поверхность: всегда зелёная, каждое утро соприкасается с ветками соседей |
| `b/<задача>` (задачные) | дни, до закрытия задачи | только владелец | в свою же dev через PR | Карантин и упаковка одной задачи: здесь можно пушить мусор, здесь ревьюер смотрит диф |
| `merge-rehearsal` | один вечер спринта 3 | A, локально | никуда | Репетиция финальных слияний, удаляется сразу |

Три инварианта, на которых держится всё остальное:

1. **`master` — только через PR, и только три раза.** Прямой push запрещён настройками репозитория; всё, что попадает в `master`, прошло CI и ревью.
2. **Dev-ветка всегда зелёная.** В неё попадает только код, прошедший ревью и CI; всё недоделанное живёт в задачной ветке. Зелёная dev — это обещание соседям, что их утренний синк не сломается.
3. **Поток чужого кода — только «втянуть к себе», поток своего — только «упаковать в PR».** Никто не пушит в чужие ветки; никто не коммитит в свою dev напрямую (кроме синк-мержей).

Направление интеграции — «втягивающее»: каждое утро каждый вливает чужое к себе, и только в последний день dev-ветки вливаются в `master`. Так выполняется требование задания («каждый работает всё время в своей ветке, сливаемся в конце») без потери ежедневной интеграции.

## 1. Первый день: инициализация

Порядок важен, потому что личные ветки обязаны родиться от `master`, уже содержащего инфраструктуру (CI, шаблон PR, `pom.xml` с JaCoCo).

Участник A выполняет bootstrap: создаёт `master` с первым коммитом, затем ветку `a/bootstrap`, в которой готовит инфраструктуру, открывает PR `a/bootstrap → master` (это единственный ранний PR в `master` — он содержит только инфраструктуру, без кода фич, поэтому не нарушает требование «работать в своей ветке»). После мержа на `master` включается защита ветки, и `master` замораживается до финала.

Затем каждый из участников (включая A) создаёт свою dev-ветку от свежего `master`:

```
git fetch origin
git checkout master
git pull origin master
git checkout -b a/dev        # у B: b/dev, у C: c/dev
git push -u origin a/dev
```

Проверка, что всё сделано правильно: в списке веток на GitHub видны `master` и три dev-ветки; попытка запушить прямо в `master` отклоняется; файл `.github/workflows/ci.yml` существует в вашей ветке.

## 2. Ежедневный ритуал: утренний синк (10 минут)

Синк — это вливание чужих dev-веток в свою. Его смысл: держать три ветки близко друг к другу всю дорогу, чтобы финальные слияния в последний день оказались дешёвыми, а интеграционные проблемы всплывали утром следующего дня, а не на защите. Порядок — «хаб»: сначала интегрирует A, затем к нему подтягиваются B и C. Причина хаба: один и тот же конфликт должен разрешаться **один раз в одном месте**, иначе B и C разрешат его по-разному и ветки разойдутся.

Шаг 1 — A вливает к себе всех:

```
git checkout a/dev
git fetch origin
git merge origin/b/dev
git merge origin/c/dev
git push origin a/dev
```

Если при `merge` возник конфликт — см. раздел 5. Пуш запускает CI на объединённом состоянии всех трёх веток: это и есть момент, когда машина ловит конфликт интеграции.

Шаг 2 — B и C вливают к себе A (внутри уже есть их собственные вчерашние коммиты, поэтому их синк почти всегда беспроблемный):

```
git checkout b/dev            # у C: c/dev
git fetch origin
git merge origin/a/dev
git push origin b/dev
```

Шаг 3 — первый пункт стендапа: «синки зелёные или красные». Красный синк — блокер дня: он чинится до начала любой новой задачи, потому что означает, что код собрался, но логика столкнулась с ошибкой (семантический конфликт), и каждый час промедления увеличивает расхождение.

Если A перегружен или отсутствует, синк может провести любой из B/C по тем же командам — принцип «один конфликт решается один раз» важнее персональной роли.

> Не отставайте от соседей больше чем на день. Чем длиннее расхождение, тем больше конфликт.

## 3. Цикл работы над задачей: от ветки до удаления

Это основной цикл, который вы будете повторять десятки раз. Одна задача бэклога = одна задачная ветка = один PR. Правило WIP: одновременно у вас в работе не больше одной задачи.

**Шаг 1 — создать задачную ветку от свежей dev.** «Свежей» — после утреннего синка; пятый пункт чеклиста PR проверяет именно это. Имя ветки: `<пользователь>/<id-задачи>`.

```
git checkout b/dev
git checkout -b b/JFP-2
```

Зачем отдельная ветка: PR (и значит — ревью, чеклист, статусы CI, кнопки Merge) существует только между ветками; кроме того, задачная ветка — карантин, в котором можно пушить промежуточное состояние и точка, на которой можно «заморозить» прерванную работу.

**Шаг 2 — работать в TDD-порядке коммитов.** Внутри своей ветки полная свобода, но при отправке на ревью порядок должен быть виден: коммит с тестом предшествует коммиту с реализацией. Удобная схема — два коммита на цикл:

```
# red: написали падающий тест
git add src/test/...
git commit -m "test(JFP-2): stack run invariants restore"
# green: минимальная реализация
git add src/master/...
git commit -m "feat(JFP-2): implement mergeCollapse invariants"
```

**Шаг 3 — отправить и открыть PR.** Важная деталь нашей конфигурации CI: пуш в задачную ветку *не* запускает проверки — CI включается только при открытии PR (триггеры: PR в dev-ветки и `master`, пуш в dev-ветки). Поэтому до открытия PR промежуточные пуши безопасны.

```
git push -u origin b/JFP-2
```

Затем на GitHub: «Compare & pull request». База PR — **ваша собственная dev-ветка** (`b/JFP-2 → b/dev`), не `master`. PR в `master` из задачной ветки — ошибка (это обход финальной церемонии). Описание PR заполняется из шаблона: ID задачи, что сделано, и чеклист, который отмечается честно — тесты видели красный; нет запрещённых API (`Arrays.sort`, `Collections.sort/binarySearch/frequency`, `Stream.sorted`, готовые паттерны); публичные методы с Javadoc; ветка создана от свежей dev; самопроверка сделана. Если работа ещё сырая, но хочется раннего взгляда — открывайте Draft PR, это честный сигнал «не мержить».

**Шаг 4 — ревью и мерж.** Ревьюером назначается коллега. Если CI красный — кнопка Merge заблокирована защитой; чините на ветке и пуште, CI перезапустится сам (перезапуск после каждого пула коммитов — норма, не «поломка»). После одобрения: метод слияния — только «Create a merge commit». Squash и rebase запрещены на всём протяжении проекта: merge-коммит сохраняет в истории видимый след ветвления, что важно и для финальной картины, и для требования задания. После мержа нажмите «Delete branch» (кнопку предлагает сам GitHub) — и локально:

```
git checkout b/dev
git branch -d b/JFP-2    # -d (маленькая) откажется удалять неслитую ветку — это защита
```

Зачем удалять: коммиты уже надёжно лежат в dev (ветка в Git — лишь указатель, удаляется указатель, не история; восстановление через `git reflog` доступно неделями), а чистый список веток автоматически поддерживает соответствие «веток с кодом = числу участников» и не оставляет мёртвых веток, в которые кто-нибудь случайно ответвится.

**Шаг 5 — следующий утренний синк разнесёт вашу задачу коллегам.** Самим «пропихивать» задачу в чужие ветки нельзя и не нужно.

## 4. Вы как ревьюер

Ревью чужого PR — часть вашей работы. Порядок: убедиться, что CI зелёный (красный — вернуть автору сразу, код не читаем); прочитать описание и чеклист; прочитать diff как чужой код, сверху вниз; проверить пункты чеклиста по содержанию — особенно порядок «тест раньше реализации» по коммитам и отсутствие запрещённых API (поиском по дифу); оставить конкретные комментарии, а не общие («переделать»). Одобрить («Approve») — только когда сами нажали бы Merge. Обратное правило: не мержите PR, который не читали.

## 5. Разрешение конфликтов

Конфликт возникает, когда вы и коллега изменили одни и те же строки. При `git merge` Git останавливается и пишет `CONFLICT (content): Merge conflict in src/...`.

Порядок действий. Первым делом — `git status`: покажет список конфликтных файлов. Затем откройте каждый файл и найдите маркеры: `<<<<<<< HEAD` … `=======` … `>>>>>>> origin/…` — сверху ваш вариант, снизу чужой. Уберите маркеры и соберите правильный итог: иногда это ваш вариант, иногда чужой, чаще — комбинация (например, у коллеги новый метод, у вас новый импорт — нужно и то, и другое). Сохраните, `git add <файл>`, после всех файлов — `git commit` (Git сам подставит сообщение мержа), затем `git push`.

Правило: *конфликт с чужим кодом разрешается вместе с его автором*, а не молча. Именно поэтому синк идёт через A-хаб: конфликт B↔C разбирается один раз у A и следующим синком расходится к обоим. Если конфликт не в коде, а в идее (два разных подхода к одному месту) — выносится на стендап, а не решается победой того, кто позже мержил.

Особый случай — «горячие файлы», в которых ветки соприкасаются физически: `Application` (composition root), карта команд меню, `BusComparators`, `pom.xml`. Правило: объявляйте изменение горячего файла в чате *до* коммита; правки `Application` согласовываются с A.

## 6. Красный CI: что делать

Красный PR (ваши изменения): упавший тест — главный источник информации; откройте лог CI, найдите имя теста и ассерт, воспроизведите локально (`mvn test -Dtest=ИмяТеста`), почините на задачной ветке, пуште. Если CI красный, а локально зелёный: проверьте с помощью `git status`, всё ли закоммичено; сравните хеши локального и удалённого коммитов (`git log -1`, GitHub показывает SHA) — самая частая причина «забыл закоммитить файл с тестом».

Красный dev после утреннего синка: это семантический конфликт интеграции — блокер дня, чинится до новых задач; вероятный виновник известен по diff последнего синка.

Красный после хотфикса коллеги на его dev: не молчите — напишите автору; ваш следующий синк принесёт фикс к вам.

## 7. Мораторий, репетиция и финальное слияние (спринт 3, дни 4–5)

**Последний обмен.** Вечером дня 4 A в последний раз вливает `b/dev` и `c/dev` в `a/dev` и пушит. После этого объявляется **мораторий**: до конца проекта никто не вливает чужое к себе. Зачем: если синкаться до самого конца, все три ветки станут идентичными и второй-третий финальный PR получат «нечего мержить» — а нам нужны три настоящих, видимых слияния. Работа при этом продолжается каждый в своей ветке.

**Репетиция.** Днём дня 4 A локально, без пуша, собирает временную ветку, чтобы увидеть конфликты заранее — церемония не должна быть импровизацией:

```
git checkout -b merge-rehearsal a/dev
git merge b/dev
git merge c/dev
git checkout a/dev
git branch -D merge-rehearsal
```

Найденные на репетиции конфликты разбираются с авторами немедленно (маленькие PR прямо в этот вечер), а не утром церемонии.

**Финальное слияние (день 5) — три последовательных PR в `master`:**

1. PR `a/dev → master`. Самый большой диф. Ревьюеры — B и C. Мерж методом «Create a merge commit».
2. PR `b/dev → master`. Диф маленький — хвост коммитов B после моратория. Ревьюеры — A и C.
3. PR `c/dev → master`. Ревьюеры — A и B.

Условия кнопки Merge для каждого: зелёный CI + хотя бы один аппрув (назначайте обоих — это финальное кросс-ревью). После третьего слияния — тег релиза:

```
git checkout master
git pull origin master
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0
```

Демо показывается именно с тега. В истории `master` после финального слияния остаются три merge-коммита «Merge branch 'b/dev'» и т.п. — это прямое, видимое доказательство выполнения требования задания о слиянии веток участников.

*Если после тега найден баг* — это нормальная, предусмотренная ситуация: фикс делается в своей dev-ветке (через обычный задачную ветку и PR, с красным тестом), затем открывается маленький PR `dev → master` — ветка может сливаться в `master` больше одного раза, требование задания от этого не страдает.

## 8. Типовые проблемы и их решения

«Случайно закоммитил прямо в dev, минуя задачную ветку». Если коммит ещё не запушен: перенесите его в задачную ветку — `git checkout -b b/quick-task`, затем верните dev назад `git checkout b/dev && git reset --hard origin/b/dev`, и продолжайте по обычному циклу. Если уже запушен и зелёный, а изменение тривиальное (опечатка в комментарии) — сообщите на стендапе; если нетривиальное — оформите задним числом PR из отдельной ветки, содержащей этот коммит, и прогоните ревью.

«Кнопка Merge не активна». Две причины: красный CI или нет аппрува. Смотрите статусы в блоке checks PR.

«Нечаянно удалил задачную ветку / потерял коммиты». `git reflog` покажет последние позиции HEAD; найдите нужный SHA и `git branch b/JFP-2 <sha>`.

«Синк каждый день конфликтный». Вы отстаёте от соседей или правите горячие файлы. Догоните (синк два дня подряд), объявляйте горячие файлы заранее, и поднимите на ретро — возможно, зоны ответственности перекрываются.

«Задачная ветка разрослась до тысячи строк». Задача недодекомпозирована. Скажите на стендапе, разбейте на две ветки/PR.

«Хочу переделать историю задачной ветки (rebase/force-push)». На задачной ветке технически можно, но новичку совет простой: *никакого force-pushа нигде и никогда*; нужно переписать историю — позовите A. Force-push в dev-ветку — запрещён безусловно (её состояние видят CI и соседи).

## 9. Шпаргалка

```
# утро (A)
git checkout a/dev && git fetch origin
git merge origin/b/dev && git merge origin/c/dev
git push origin a/dev

# утро (B, C)
git checkout b/dev && git fetch origin
git merge origin/a/dev && git push origin b/dev

# старт задачи
git checkout b/dev && git checkout -b b/JFP-2
git push -u origin b/JFP-2

# конфликт
git status                # список конфликтных файлов
# правим файлы, убираем <<<<<<< ======= >>>>>>>
git add <файлы> && git commit && git push

# закрытие задачи (после Merge на GitHub)
git checkout b/dev && git branch -d b/JFP-2

# локальная проверка перед пушем
mvn test
```

## 10. Свод правил «всегда / никогда»

| Всегда | Никогда |
|---|---|
| Синк каждое утро; красный синк — блокер дня | Не отставать от соседей больше чем на день |
| Задачная ветка — от свежей dev, PR — в свою же dev | Коммитить прямо в dev (кроме синков) |
| Тест раньше реализации в порядке коммитов | Мержить непрочитанный PR; ставить галочки чеклиста «на потом» |
| Конфликт с чужим кодом разрешается вместе с автором | Разрешать конфликт молча, «выиграв» его |
| Merge-коммит как единственный метод слияния | Squash, rebase-merge, force-push (без A) |
| Удалять задачную ветку после слияния | Держать мёртвые ветки в списке |
| PR в `master` — только три финальных (+возможные хотфиксы) | PR из задачной ветки в `master`; прямой push в `master` |
| Объявлять правки горячих файлов в чате до коммита | Молча менять `Application`, карту команд, `pom.xml` |
